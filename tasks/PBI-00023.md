# PBI-00023: Run the whole pipe in CI and keep the report

## Directive

Make CI run `bcr extract | bcr verify | bcr audit | bcr report` on
every push, show the page `bcr report` writes in the job's summary,
and keep it as an artifact of the run, so that every push leaves a
report, whether the job fails or not.

**Scope:**
- In `.github/workflows/check.yml`, end the pipe with `bcr report`,
  writing the page to `$RUNNER_TEMP/report.md` in place of
  `/dev/null`. The pipe still runs under `set -o pipefail`, so a
  problem or a Refuted claim still fails the job, through the exit
  status of `bcr extract`, `bcr verify` or `bcr audit`; `bcr report`
  exits 0 whatever the verdicts.
- Add two steps that run unless the run is cancelled, a failed job
  included:
  - append the page to `$GITHUB_STEP_SUMMARY`, when it is not empty;
  - upload it with `actions/upload-artifact`, pinned to the commit of
    v7.0.2, as the file itself (`archive: false`), ignoring a page
    that was never written, such as after a failed build.
- In `specs/asdlc/spec.md`, say under Architecture what CI runs, add
  a Regression Guardrail that CI runs the whole pipe, and guard it
  with a `has-line` claim on the line of `check.yml` that runs it
  (ADR-0019). Removing `bcr report` from CI, or the pipe, turns the
  claim Refuted.
- Leave AGENTS.md's Toolchain and the Definition of Done as they are:
  the three-stage check is what a change must pass, and `bcr report`
  adds no verdict to it.

## Verification
- [ ] `.github/workflows/check.yml` is valid YAML, and every action it
      uses is pinned to a commit.
- [ ] `set -o pipefail; go run ./cmd/bcr extract | go run ./cmd/bcr verify | go run ./cmd/bcr audit > /dev/null`
      prints nothing and exits 0, with the new claim Confirmed.
- [ ] The claim holds by hand:
      ```
      sed 's/\r$//; s/^[[:blank:]]*//; s/[[:blank:]]*$//' .github/workflows/check.yml | grep -xF -- '"$RUNNER_TEMP/bcr" extract | "$RUNNER_TEMP/bcr" verify | "$RUNNER_TEMP/bcr" audit | "$RUNNER_TEMP/bcr" report > "$RUNNER_TEMP/report.md"' > /dev/null
      ```
- [ ] On the first push, the job's summary shows the page, and the
      run keeps `report.md` as an artifact. Whether GitHub draws its
      Mermaid diagrams there is noted for the plan: the artifact is the
      page either way.

## Refinement Protocol
If the job's summary or the artifact needs a permission the workflow
does not have, stop and ask: the workflow reads the repository only.
