# ADR-0030: The site is generated with Hugo, pinned to one release

Status: Accepted
Date: 2026-10-10

## Context

Breadcrumb has a release, v0.9.0, and no entry point for someone who
has not cloned the repository. The site's job is to pitch the method
and `bcr` to possible adopters, and to host the documentation
(`docs/bcr.md`, ADR-0008) online. Its text is prose with a menu of
anchors, and its documentation page already exists as Markdown.

A site needs either a generator or hand-written HTML. Hand-written
HTML is a cost that grows with every page, and `docs/bcr.md` would
need a Markdown converter that this repository owns. This repository
once kept such a generator, `cmd/specsite`, and deleted it with the
old model (ADR-0024).

Hugo is a Go program, so it fits the toolchain, but it is not a Go
module that `bcr` requires: it adds nothing to `go.mod`, and ADR-0005
does not apply. It is still something the repository does not
control, and a new release can change what it builds without any
commit here.

## Decision

- The site is generated by Hugo from Markdown under `site/`, a
  directory at the root of the repository.
- Hugo is pinned to one exact release, in the workflow that builds the
  site (ADR-0031). It is the standard edition: the site uses plain
  CSS and needs no SCSS. A new release is a deliberate change to that
  workflow.
- The site uses no theme and fetches no Hugo module. Its layouts are
  in `site/layouts/`.
- Hugo is not needed to build, test or run `bcr`.
- The ids of the landing page's sections are written in its Markdown,
  as in `## The problem {#problem}`. Its menu is written in
  `site/hugo.toml`.
- The documentation page is `docs/bcr.md`, copied to
  `site/content/docs/_index.md` when the site is built. The copy is
  not committed and is never edited, so the documentation has one
  source.
- The site loads nothing from outside itself, no font, script, style
  or image, and its menu works without JavaScript.

## Consequences

- Moving to a newer Hugo changes one line of the workflow, which a
  reviewer sees in the diff. As with a module's version (ADR-0005),
  it needs no ADR; replacing Hugo with another generator does.
- Someone who wants to preview the site needs Hugo installed. Someone
  who runs `bcr` does not.
- The headings of the documentation page get the ids Hugo derives
  from their text, so `### extract` is reached at `#extract`. If a
  Hugo release changes how it derives them, links to the page break;
  the pin keeps that from happening unseen.
- The built site is not in the repository. A reader matches it to the
  repository through the tag and commit it records (ADR-0031).

## Alternatives Considered

- Hand-written HTML, with a converter for `docs/bcr.md` written here:
  nothing to pin, but a Markdown parser and the templates become code
  to maintain.
- Jekyll, built by GitHub Pages: no workflow, but Pages can publish
  only the root or `docs/`, not `site/`, and it chooses the Jekyll
  version, which can change without a commit.
- A generator written in Go and kept in this repository, as
  `cmd/specsite` was: no outside tool, but the repository would again
  maintain a site generator beside `bcr`.
- Hugo extended edition: needed only for SCSS, which the site does not
  use.
- A Hugo theme or module fetched from the web: less to write, but code
  the repository does not control would enter the build on every run.
