# TD-0030: How the specification is versioned

Parent: [IN-0015](IN-0015.md)

## Decision

The specification's version is `MAJOR.MINOR.PATCH`, apart from the
version of `bcr`. It changes only when a rule of the method changes;
a change of wording that leaves every rule as it was keeps the
version.

Until 1.0.0, every change to a rule raises `MINOR` and sets `PATCH`
to 0. After 1.0.0, a change that makes a breadcrumb that followed the
rules no longer follow them raises `MAJOR`, and any other change to a
rule raises `MINOR`.

A change that changes a rule raises the version in the same commit.
Its Task claims the new version line.

The first version is 0.2.0, since 0.1.0 names an earlier
specification in the history of this repository.

## Why

An adopter pins the rules its breadcrumbs follow, not a build of a
tool. With its own version, a fix to `bcr` alone does not look like a
change to the method (IN-0015).

Raised in the commit that changes the rule, the version cannot fall
behind the rules, and the Task's claim shows where it changed.

## What it beat

- The version of `bcr`: every fix to the tool would look like a new
  method.
- Raising the version at release: a change to a rule could reach a
  release under the version before it.
- Dropping the version and naming the specification by the `bcr`
  release: an adopter could not tell whether two releases follow the
  same rules.
