# TD-0028: Write the specification now, from the model

Parent: [IN-0013](IN-0013.md)

## Decision

The specification of Breadcrumb SDD is written now, in
`docs/breadcrumb-sdd.md`, before a repository other than this one
adopts the method. This replaces the moment TD-0007 set for it; the
rest of TD-0007 holds.

It is derived from the model in `internal/breadcrumb` and from the
breadcrumbs that decided it. It states the rules of the method for any
repository: which files are breadcrumbs, what each holds, how they
link, and how they are audited. It leaves out what only this
repository decided, such as its language, license and commit
messages, and the interface of `bcr`, which is the contract
(TD-0018).

Once written, the specification defines the method, and the model
carries it out. Where the two disagree, that is drift, and the change
that finds it fixes one of them or records a new decision. A Task
claims both the rule in the specification and the line of the model
that carries it out, so a change to either one alone shows as
Refuted.

Each section names the breadcrumbs its rules come from.

## Why

TD-0007 waits for another repository to adopt the method, because
such a repository is the first reader that cannot be expected to read
this code. But a repository cannot adopt a method it can only learn
from this code, so the wait has no end. Writing the specification is
part of making adoption possible.

The model now covers every kind of breadcrumb, their links, the only
kind of claim, and the verdicts, and `bcr` has a contract. There is
enough working software to derive from.

## What it beat

- Waiting for an adopter, as TD-0007 says: an adopter would have to
  read Go to learn the method.
- The model staying the definition, with the specification as a
  description of it: an adopter could not tell a rule from a detail
  of one tool.
- Stating the rules in the specification only, without Task claims on
  the model: the specification and the model would drift apart
  unseen, which TD-0007 warned against.
