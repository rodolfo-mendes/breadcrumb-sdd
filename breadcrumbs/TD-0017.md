# TD-0017: Build release binaries with GitHub Actions on each tag

Parent: [IN-0003](IN-0003.md)

## Decision

Pushing a tag that starts with `v` runs the workflow in
`.github/workflows/release.yml`. It runs the tests, then builds `bcr`
for Linux, macOS and Windows, each on x86-64 and ARM64, as static
binaries (`CGO_ENABLED=0`). Each binary is packed with `LICENSE` and
`README.md`, as a `.tar.gz`, or a `.zip` on Windows, named
`bcr_<version>_<os>_<arch>`, beside a file of SHA-256 checksums.

The archives are attached to the tag's GitHub release. When the
release does not exist yet, the workflow creates it with notes
generated from the commits; when it exists, its notes are kept and
its archives are replaced.

The workflow can also be run by hand for an existing tag.

Actions are pinned to a commit.

## Why

IN-0003 asks that a developer need nothing installed but `bcr`, so
each release needs a binary per system. Built by hand, each release
depends on one machine and on remembering the steps.

## What it beat

- A build script run by hand: repeatable, but a release still waits
  on one person's machine.
- GoReleaser: builds, archives and checksums in one tool, but it is a
  dependency to trust and configure for six builds a short loop does.
- Signing the binaries: macOS and Windows warn about unsigned
  binaries, but signing needs paid certificates.
