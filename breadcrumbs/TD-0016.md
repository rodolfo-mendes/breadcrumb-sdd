# TD-0016: Write commit messages as Conventional Commits

## Decision

Commit messages follow Conventional Commits 1.0.0, with three types:

- `feat`: the change adds to or changes what the software does.
- `fix`: the change corrects something that does not work as
  intended.
- `docs`: the change touches only prose, such as the README or the
  contributor guide, and leaves what the software does unchanged.

The description says what the change does, in the imperative. The
body says what changed, lists each breadcrumb the commit adds or
changes with a line on what it records, and ends with how to verify
the change.

## Why

Conventional Commits is widely known, so a contributor can follow it
without learning a format made up here. Its type tells a reader at a
glance whether a commit adds something, corrects it, or only changes
its prose.

Listing the breadcrumbs in the body lets a reader get from a commit to
its intent. Most commits so far have this shape.

## What it beat

- Only `feat`: every commit so far has used it, but it calls a
  correction a feature.
- The full set of common types, adding `chore`, `refactor` and more:
  no change here has needed one yet, and each type is one more choice
  for every commit.
- A free-form subject: nothing tells a reader what kind of change a
  commit is.
