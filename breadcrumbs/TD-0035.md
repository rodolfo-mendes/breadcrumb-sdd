# TD-0035: The check runs on GitHub Actions with the same bcr

Parent: [IN-0017](IN-0017.md)

## Decision

The check `bcr init` sets up is a GitHub Actions workflow, the only
one it writes. It downloads the Linux x86-64 archive of the release
of `bcr` that ran `bcr init` (TD-0017), checks it against the
release's checksums, and runs that binary. Its actions are pinned to
a commit.

A repository on another CI runs the same two commands, as the
contract shows.

## Why

The check should carry out the same version of the specification as
`bcr init` pointed agents to, so it runs the same release, not the
latest.

A release binary needs nothing installed, as IN-0003 asks; an
adopter's CI may have no Go.

GitHub Actions is where this repository and most open repositories
run. A workflow file does nothing on another host.

## What it beat

- `go install` of `bcr` in the workflow: it needs Go on the runner,
  and builds `bcr` on each run.
- A flag to choose among CI systems: one system is all anyone has
  asked for, and each more is a template to keep working.
- Only printing the commands to run: the step most likely to be
  missed would be left to the user.
