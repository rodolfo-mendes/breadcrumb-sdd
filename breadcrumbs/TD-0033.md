# TD-0033: Deploy the site with a workflow that follows the release

Parent: [IN-0016](IN-0016.md)

## Decision

A workflow in `.github/workflows/pages.yml` runs when the release
workflow completes successfully (`workflow_run`), and by hand
(`workflow_dispatch`). It fetches every tag, runs
`go run ./cmd/specsite`, and deploys the directory it writes with
GitHub's Pages actions, pinned to a commit as in TD-0017.

The repository's Pages are set, once, to be deployed from GitHub
Actions.

## Why

Following the release, a page is only published for a tag whose
tests passed and whose binaries were built. A `workflow_run` workflow
runs on the default branch, which the `github-pages` environment
allows to deploy; a run on a tag would need a rule of its own.

A workflow of its own keeps the permissions Pages needs, to write
Pages and to get an identity token, away from the release.

## What it beat

- A job in the release workflow: the release would carry the Pages
  permissions, and a failed deploy would fail the release.
- Running on each `v` tag directly: it would race the release, and
  the environment would need a rule for tags.
- Deploying on each push to `main`: the site would show rules no
  release carries yet.
